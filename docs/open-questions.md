## A. 需要拍板

### A1 是否做用户系统，身份从哪来

- **现状**：没有用户表，也没有登录。所有资料挂在固定主体 `demo-owner` 下；令牌是启动时随机密钥签的，通过地址栏 `#t=` 一次性传入，刷新页面即失效。代码里 `Actor.subject_id` 是唯一身份来源，目前恒等于 `demo-owner`。
- **为什么是问题**：只要不接真实账号，就无法回答「这份资料谁能看」「换台电脑还是不是我的库」。一旦接入真实人员，权限模型、数据归属、审计都要跟着改。
- **可选方案**
  1. **不建用户系统**（保持单用户本机工具）：最简单，但只能一个人用；
  2. **接入宿主系统的身份**：知识服务只认 `subject_id`，账号、登录、组织关系都由外层负责（design §11 的方向）；
  3. **自建轻量账号**（邮箱/口令或验证码）：多一套账号体系要维护，与「主系统内的模块」定位冲突。
- **建议**：选 2。本服务不实现登录，只接受可信主体标识；本机场景用启动器下发的临时令牌即可。
- **谁定**：负责人 + 宿主系统侧（身份由谁签发、`subject_id` 由谁写入）。

### A2 QwenPaw 接入形态仍未定

- **现状**：`decisions.md` 0008 状态「待定」；`entrypoints/mcp.py` 仍是占位；`integrations/qwenpaw/` 目录未建。工具面（6 个）已在 `mcp/tools.py` 固定。
- **为什么是问题**：这是 MVP 计划内唯一没动工的部分，方案不定就无法开工。
- **可选方案**：MCP + Skill（跨进程，标准协议）／进程内 Plugin（耦合紧，集成快）。
- **建议**：MCP + Skill。工具面已定，协议层工作量可控，且不 fork 上游仓库。
- **谁定**：负责人。

### A3 接入真实资料的三个前置边界

- **现状**：仓库内只有自制测试资料；真实资料从未进入系统。
- **三个待定**：① 什么内容允许发给外部模型（整段？摘要？只发命中片段？）；② 是否需要审计表（谁在什么时候问了什么）；③ 问答与日志保留多久。
- **为什么是问题**：这三项不定，安全模型无法收口；先接资料再补，代价是返工与合规风险。
- **建议**：① 只发命中片段，不发整篇；② 先落「请求级」审计（不含正文），保留 90 天；③ 会话正文默认不落盘，仅存引用关系。
- **谁定**：负责人 + 合规/安全。

### A4 部署形态：继续本机，还是回到服务端

- **现状**：10-29 起默认用本机 PostgreSQL（`backend/.data/pgdata`，端口 55433），不再连远端；`decisions.md` 0019 已记录，并写明重审条件。
- **为什么是问题**：本机库解决了网络抖动与外部依赖，但天然不支持多人共享、跨机备份、多实例。
- **可选方案**：① 维持本机（单人/演示）；② 单机 + 服务端库（多人共享同一份资料）；③ 完整服务端部署（多实例、对象存储）。
- **建议**：演示与个人使用维持 ①；一旦要「多人看同一批资料」，直接跳到 ②，不必先做 ③。
- **谁定**：负责人（取决于交付形态是「本机工具」还是「团队服务」）。

## B. 需要定标准

### B1 「没有答案」怎么判定

- **现状**：靠两道路径——证据分数低于阈值直接判无依据；模型自己返回空段落时也按无依据处理（今天刚修，此前会报成 502）。但**主题相邻**的问题仍会拿到「相关但不含答案」的分块（`ISS-011`，bge-m3 实测相似度无法分隔 0.350 与 0.393）。
- **为什么是问题**：这决定用户看到的是「诚实拒答」还是「看起来有据的错误答案」，是产品可信度的底线。
- **可选方案**：① 引入重排模型（bge-reranker）做答案级判别；② 生成端增加「证据是否支持结论」的自检；③ 维持现状，用阈值 + 用户自查。
- **建议**：先做 ②（成本低、与现有引用校验同层），效果不足再上 ①。
- **谁定**：负责人定投入，我出方案与评测。

### B2 关键词检索是保留、降权还是换掉

- **现状**：500 块语料实测，真实命中与语料外问题的 trigram 相似度分布完全重叠（0.058 vs 0.059），`ISS-010` 判定**已触发**设计里的事先约定；目前靠语义路兜底。
- **为什么是问题**：语义模型不可用时没有退路；专名、文号这类查询也失去精确优势。
- **可选方案**：① 换分词器 + tsvector；② 关键词路只保留专名/文号场景并降权；③ 直接下线关键词路。
- **建议**：①，但要先有中文分词依赖；短期先做 ② 止血。
- **谁定**：负责人定优先级。

### B3 版本与代次保留多久

- **现状**：每次上传新版本代次 +1，旧版本仍可检索，直到新版本发布；系统没有清理策略，历史版本与构建一直留着。
- **为什么是问题**：长期使用会累积原件与向量；「保留几版」也是用户预期问题（能不能回滚到上一版）。
- **可选方案**：① 永久保留（简单，占空间）；② 只保留最近 N 版；③ 保留全部元数据但清理最早的原件。
- **建议**：②，N=5，并在文档里写明可回滚范围。
- **谁定**：负责人。

### B4 支持格式的承诺边界

- **现状**：PDF / DOCX / XLSX / Markdown / TXT / 图片（含 TIFF）可解析；XLSX 与 TIFF 已能在页面内预览。**`.xls`（旧版 Excel）不支持，上传即被拒**；PPTX 走 DeepDoc，需 Docker 边车。
- **为什么是问题**：用户手里往往是 `.xls`、`.ppt`、扫描件混在一起，「支持 Office」这句话很容易被理解成全都支持。
- **可选方案**：① 明确列出支持清单并在上传处提示；② 补 `.xls`（加依赖）与 `.ppt`；③ 统一先转 PDF 再入库。
- **建议**：①，外加「不支持时给出明确下一步」；② 按需再说。
- **谁定**：负责人（承诺范围）。
