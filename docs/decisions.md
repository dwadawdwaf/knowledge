## 0001 三标识分离

**决定** `document_id` 表达「这份资料」，`version_id` 表达一次不可变上传，`build_id` 表达一次索引构建。文档持有 `current_version_id` / `active_build_id` / `pending_build_id` 三个指针，检索只读 `active_build_id`。

**为什么** 一份资料会同时经历三种变化：改标题、换正文、换分段或向量模型。用一个 ID 加「最新内容」指针表达不了这三种，结果是引用指向错内容、重建索引污染版本历史、删除时不知删哪份。

**被否**

| 方案 | 理由 |
| --- | --- |
| 只有 document + content，更新即覆盖 | 无法回答引用出自哪一版；更新后历史引用失效 |
| 两层，重建索引也新建 version | 把系统配置变化伪装成用户内容变化 |
| 内容寻址存储（hash 作标识） | `sha256` 已用于去重；再加一层寻址增加查询路径，跨库共享场景不存在 |

**重审条件** 出现「同一内容被多个知识库共用且要求去重存储」，或「同版本需并行保留多套索引供 A/B」。

## 0002 索引构建发布后不可变

**决定** `state = ready` 的 build 及其 chunks 只读。重试与重建一律新建 build；失败重试只清理本次 attempt 未发布的暂存数据；旧 build 置 `retired`，不再检索但保留供历史引用追溯。

**为什么** 分块与向量化会失败，最省事的做法是清掉重跑。但检索可能正在进行，删改已发布数据会让引用定位失效，且无法解释两次失败之间内容为何不同。

**被否**

| 方案 | 理由 |
| --- | --- |
| 原地 delete + insert | 检索会看到半成品；发布失败时旧内容已毁，无回退路径 |
| 软删除标记 + 查询时过滤 | 依赖每条查询都加条件，一处遗漏即泄露；仍解决不了同 build 内版本混杂 |
| 每次发布快照整库 | 存储与迁移成本随规模线性增长 |

**重审条件** 单文档构建数量影响查询性能且 `retired` 保留期已有策略；或实测存储成本要求引入构建级 TTL。

## 0003 发布栅栏由 generation 与租约共同保证

**决定** 发布必须同时满足：持有有效 `lease_token` 且租约未过期、`generation` 与文档一致、`pending_build_id` 未变。三者在一个事务内校验并切换，任一不满足则任务置 `cancelled`。

**为什么** 构建可能耗时数分钟。期间用户可能上传了新版本、删除了文档，或前一个 Worker 已崩溃。只校验「这个 build 属于这个文档」会让迟到任务把过时内容重新设为生效版本——资料已删除却被复活。

**被否**

| 方案 | 理由 |
| --- | --- |
| 只用租约 | 租约只证明执行者活着，不证明目标仍有效 |
| 用 `updated_at` 比较 | 时钟与精度问题导致误判，并发写入无法区分先后 |
| 行锁覆盖整个构建 | 持锁数分钟阻塞写入，崩溃后行为不可预测 |
| 外部协调服务 | 单机规模下新增故障域，收益不足 |

**重审条件** 多个 Worker 并行且行锁成为实测瓶颈；或需要「并行构建多个候选索引、人工选择发布」。

## 0004 关键词通路使用 pg_trgm

**决定** `chunks.tsv` 存参与匹配的原文副本，建 `GIN (tsv gin_trgm_ops)`；按查询与文本的三元组相似度排序，同分按 `ordinal`；与语义路用 RRF 融合。

**为什么** 混合检索需要关键词路兜住专名、文号、精确短语，而 PostgreSQL 内置全文检索不切分中文。分词方案需要编译扩展或维护两处分词版本，在缺少实测数据时不适合作为第一版依赖。

**被否**

| 方案 | 理由 |
| --- | --- |
| zhparser 等分词扩展 | 需编译与词典维护；一旦不可用整条链路失效 |
| 应用层 jieba 分词 + tsvector | 分词版本必须两端严格一致，否则召回断裂 |
| 仅 `ILIKE` | 无法排序，长文本性能差 |
| 只做向量检索 | 系统性漏掉文号、编号、精确条款类查询 |

**重审条件** 关键词路 `Recall@K` 显著低于语义路，且失败样本集中在需要词项权重而非字符重叠的查询。

## 0005 用数据库任务表代替消息队列

**决定** `jobs` 表即任务系统：任务与业务记录同事务创建；Worker 用 `FOR UPDATE SKIP LOCKED` 领取；用 `lease_token` + 过期时间 + 心跳实现恢复；`available_at` 实现退避。

**为什么** 引入队列意味着两个持久化系统，需要处理双写不一致；补救方案（事务消息、outbox、对账）都比一张任务表复杂。当前没有吞吐压力证据。

**被否**

| 方案 | 理由 |
| --- | --- |
| Celery + Redis / RabbitMQ | 增加必须持久化的组件；双写一致性需额外机制 |
| 进程内后台任务 | 进程退出即丢任务，无法崩溃恢复 |
| 系统定时任务扫表 | 并发控制靠外部，不如行锁精确 |
| Temporal 等任务服务 | 能力与概念负担远超当前需求 |

**重审条件** 单 Worker 排队中位数超过 5 分钟，或需要优先级、定时调度、跨机分片；升级时保留 `jobs` 表作为状态真相，队列只承担投递。

## 0006 引用由服务端分配与校验

**决定** 服务端为每个送检分块分配 `evidence_key`，模型只输出 `sections[].evidence_keys`；服务端校验键属于本轮输入、从原文截取 `excerpt`、组装引用对象。模型不接触 ID、路径或 URL。

**为什么** 让模型在答案里附来源，它会编造文件名、页码和条款号，而这类错误在界面上与真实引用无法区分。资料删除后，这些「引用」还会继续存在。

**被否**

| 方案 | 理由 |
| --- | --- |
| 模型输出链接或文件名，事后解析 | 解析规则必然不完备；编造内容与真实内容结构相同 |
| 用后置相似度为答案补引用 | 匹配「看起来相关」而非实际参与生成的内容 |
| 只展示命中列表，不做答案级引用 | 用户无法判断哪句话对应哪份依据 |
| 依赖供应商 grounding 回传 | 行为随模型版本变化，不能作为契约 |

**重审条件** 宿主模型能跨模型稳定输出结构化 grounding；或产品明确接受「未校验引用」并愿意在界面区分。

## 0007 删除拆为逻辑阻断与物理清理

**决定** 逻辑删除在同步事务内完成：置 `deleting`、`generation` 递增、清空发布指针、取消未完成任务、建 cleanup job，此后立即不可访问。物理清理异步执行，删除原件、分块、构建、版本后置 `deleted`。

**为什么** 内容散落在原件、分块、向量、历史引用与历史答复多处，同步删完会让接口耗时不可控，且任一步失败就出现「部分删了」。阻断效果不应依赖清理是否成功。

**被否**

| 方案 | 理由 |
| --- | --- |
| 同步删全部数据 | 响应时间不可控；对象存储失败会留下记录已删而文件残留 |
| 只标记删除、永不清理 | 存储无限增长，无法满足删除要求 |
| 先物理删除再标记 | 中途失败留下「可访问但内容缺失」的破裂状态 |
| 软删除 + 全查询过滤 | 依赖每条查询记得加条件，无法表达「清理进行中」 |

**重审条件** 出现「保留期内可恢复删除」的回收站需求；或对象存储提供强一致即时删除，同步删除的失败风险可消除。

## 0008 QwenPaw 以 MCP 服务 + Skill 包接入

**状态** 待定 —— 接入形态需项目负责人确认后落定。

**背景** 宿主的扩展方式有四种，能力差异影响调用是否跨进程、能否取得上下文、升级耦合程度：

| 能力 | MCP + Skill | Plugin（进程内） | 源码级改动 |
| --- | --- | --- | --- |
| 暴露工具 | 是 | 是 | 是 |
| 读取 agent / workspace 上下文 | 需调用方传参 | 可直接读取 | 可直接读取 |
| 推理前注入检索结果 | 否 | 是（`register_middleware`） | 是 |
| 复用宿主工具审批 | 否 | 是 | 是 |
| 升级耦合 | 低 | 中 | 高 |

**当前决定** 按 MCP 服务 + Skill 包描述与实现，QwenPaw 源码不改动。`Plugin` 已核实进程内运行、通过 `PluginApi.register_tool` 注册，若后续需要上下文注入或按 agent 配额，再切换。

**无论哪种形态都成立**

1. `services` 不依赖 HTTP，两个入口共用同一套业务方法；
2. 工具面固定 6 个；
3. `subject_id` 只来自集成侧配置与已验证令牌；
4. 引用只指向 `document → version → build → chunk`，ReMe 记忆不作证据；
5. 资源隔离由本服务自己完成，不依赖宿主访问控制；
6. 解析与向量化在独立进程执行，不占用宿主运行时。

**重审条件** 需要把检索结果注入 Agent 上下文，或需按 agent 粒度做配额时，重新比较两种形态成本；形态确认后本文状态改为「已接受」。

## 0009 审计修复：固定任务目标与事务栅栏

**状态** 已接受，2026-10-25，经项目负责人确认。

**决定** jobs 增加 build_id / generation；每次尝试绑定目标。重试新建 build，
累计尝试次数不重置；每轮领取前回收过期租约。document → job → build 为统一锁顺序，
分块写入、发布与任务成功同事务。具体语义见 design.md §4.7、§5.3。

**为什么** 修复旧任务接管新版本、过期执行者继续写入、快速重启丢失回收和发布双提交问题。

**被否方案** 继续读取当前 pending 指针；只校验心跳；发布后另行更新任务；引入额外消息队列。

**迁移** 先停止上传、排空或人工处置未完成 ingest/reindex，再停止 Worker 后升级。
迁移遇到未完成构建任务时拒绝执行，不猜测历史任务对应的 build。已结束任务允许空目标。

**重审条件** 引入跨数据库发布或分布式任务系统时重新评估事务边界。

## 0012 最新上传版本的同模型重建与人工恢复

**状态** 已接受，2026-10-26，经用户逐项确认契约后实施。

**决定** 增加一个受授权的重建用例同时覆盖主动重建与终态失败恢复。
仅重建最新上传版本，沿用其原始分段/向量配置；新建 build 与 reindex job，复用原文件和版本。
接口字段、错误码和并发语义统一见 design §7.1，操作说明见 runbook §11。

**为什么** 同字节上传去重不是可靠恢复入口；覆盖旧构建会污染引用，
取消已有任务则增加竞争和误操作风险。明确 version_id 避免误将旧发布版本当作失败的最新上传版本。
文档锁和 generation 比较串行化提交，并刷新 Session 中可能预载的旧对象；
既有任务表、Worker、租约栅栏及原子发布链路无需重写。

**被否方案** 以重传同字节触发恢复；原地清空失败/ready 构建；重置历史 job 的重试计数；
默认回滚到任意旧版本；新增独立重试/重建接口或幂等表；在线更换向量模型。

**边界** 不增加表、迁移、依赖或服务组件，不接 MCP；历史失败 job 保留失败结果。
无可用旧发布版本时，恢复完成前仍无证据；上游故障不会因此被包装成资料无答案。

**重审条件** 需要历史回滚、改变分段配置、跨模型迁移或客户端稳定请求幂等时，
另行确认契约与迁移方案，不扩大本接口的既有语义。
